Records developer documentation

Build on a system of record with a journal

Records is a Postgres-backed datastore service. Each datastore is an instance of a module with its own data model and REST API. The first module is Projects, and its API also speaks a subset of Jira's.

Every write goes through one command bus, in one transaction, and lands in an append-only journal ordered by a per-datastore clock. That single sequence number is your cursor for change feeds, the cookie for optimistic sync, the key for webhooks and the point you restore to.

Records in plain words

Records keeps an organisation's projects and tasks in one place that many tools can read and write: your own apps, Jira scripts and clients, and cloudflare-os gadgets. It keeps a history of every change, with who made it, when and from which tool. It has no board of its own; the tools your team already uses sit on top of it.

WordMeaning
DatastoreOne shared set of projects and tasks, owned by the organisation rather than by any tool. Usually one per department.
Project, issueA project groups tasks under a key such as ENG. Tasks are called issues, as in Jira, and are numbered ENG-12.
History (journal)Every change, in order, with the old and new values, the person and the tool. Each change gets the next number in the datastore, called its seq.
Member, roleA person with access to a datastore, as reader, editor, admin or owner. A data administrator creates datastores and picks their owners.
PrincipalAnyone who can act: a person (a member) or a service key.
Connection, bindingA tool's limited permission to use one datastore. In cloudflare-os a gadget's connection is called a binding.

Datastores and modules

Portable

An organisation owns datastores. A datastore is an instance of a module. The module owns the tables, commands, permissions and API. The core underneath is shared: registry, memberships, credentials, journal, clock, identity, idempotency and sync.

ModuleData modelAPI modelled onStatus
ProjectsProjects, issues, workflow states and transitions, comments, custom fieldsJiraBuilt
FinanceAccounts, contacts, invoices, paymentsXeroIllustration only
Message boardChannels, threads, messages, reactionsSlackIllustration only

Records belong to the organisation. Removing a client, a connection or the person who created a datastore never deletes its records. A datastore is archived, not deleted; purging is a separate administrative workflow recorded in the audit log.

Every row carries org_id and datastore_id, and row-level security keys on both. The schema is multi-organisation, so one database can hold many tenants.

Roles and scopes

Portable

Effective authority for any call is the intersection of three sets:

principal's role  ∩  credential or binding scopes  ∩  the operation's permission

Scopes only ever narrow what the principal already holds. There is no catch-all write scope. The same check runs twice: once in the command bus and again in Postgres through records.can(), so a service bug that skips a check still cannot read rows the principal has no grant for.

Permissionreadereditoradminowner
projects.read, issues.read✓✓✓✓
issues.create, issues.edit, issues.transition, comments.create✓✓✓
projects.manage, members.manage, bindings.manage, credentials.manage, audit.read, export.run✓✓
lifecycle.manage, ownership.transfer, datastore.purge✓

The organisation data_admin role creates datastores and assigns owners. It holds no record permission by itself: reading records needs a membership like anyone else.

Journal and clock

Portable

Each write transaction takes the datastore's clock as its last step, so seq is gapless and in commit order within a datastore. A client that has seen seq 41 has seen everything up to 41. Writes to different datastores never contend.

Current tables stay cheap to read. Each change also writes immutable journal rows in the same transaction. A deferred constraint refuses any current-row write that lacks its journal row, whichever code path made it.

{
  "seq": 42, "ordinal": 0,
  "changeId": "0192f3b0-…",
  "command": "projects.transitionIssue",
  "entityType": "issue", "entityId": "0192f3a9-…", "entityRev": 4,
  "op": "update",
  "before": { "state": "in_progress" },
  "after":  { "state": "done" },
  "actorId": "…principal", "actId": "…binding or null",
  "via": "http",            // gadget | http | sync | jira | management | system
  "occurredAt": "2026-09-25T10:14:03.221Z"
}

Journal ops are create, update, archive, restore and redact. The journal stores principal IDs, not names or emails, so erasing a person means removing their registry details. Redaction of free text is the one sanctioned exception to immutability, and it writes its own journal entry.

Revisions and idempotency

Portable
  • Every mutation needs an Idempotency-Key of 8–128 characters. The same key with the same body returns the saved outcome and Idempotent-Replayed: true. The same key with a different body is 409 idempotency_conflict. Outcomes are kept for 7 days.
  • Every record has a revision that increments on each change. Reads return it as ETag: "r<revision>". Changes to an existing record need If-Match with that ETag. A missing header is 428 revision_required; a stale one is 412 revision_conflict, and the response's ETag carries the current revision.
  • Creates may carry a client-chosen id, so an optimistic create keeps its identity after the server confirms it.

Service credentials

Portable

A service credential is a service principal with fixed scopes on one datastore. Its format is rk1_<32 hex>_<43 base64url>. It is shown once, stored as a SHA-256 digest, expires in 1–365 days, and stops working when revoked or when its human owner loses credentials.manage.

Send it as Authorization: Bearer rk1_…. Jira clients may send HTTP Basic with any email as the user and the credential as the password. Basic with any other password is refused.

The datastore ID in the path is only a selector. It must equal the credential's datastore, or the request is refused.

Trusted issuers

Portable

Records also accepts JWTs from issuers listed in records.trusted_issuers. Each subject must be mapped to a principal in records.identity_mappings (issuer, subject). An unmapped subject is refused; nothing is provisioned from a token.

CallerCredentialBecomes
A person in a partner appDelegated token: ES256 JWT, typ: records-delegated+jwt, 60 s, single-use jti, aud: records-datastoreThat person, narrowed to the act binding's scopes
A person in a browser UIOIDC token from Cloudflare Access for SaaSThat person
A script behind AccessCf-Access-Jwt-Assertion for the API's Access appThe mapped person or service principal
A backend servicerk1_…A service principal

Precedence: an Authorization header wins. If it is present but invalid, the request is refused and never falls back to the Access header. A JWKS or replay store that cannot be reached fails closed with 503 unavailable.

Today: the only delegated-token issuer is the cloudflare-os Records gatekeeper. The token format is open, so another platform could become an issuer by publishing a JWKS and being added to trusted_issuers.

Front door

Cloudflare runtime

On Cloudflare, a service credential needs two independent checks: the rk1_ credential and a Cloudflare Access assertion for the API's own path-specific Access application. Scripts usually get the assertion by sending an Access service token (CF-Access-Client-Id and CF-Access-Client-Secret).

The Node server makes the first factor a choice with no default: verify Access with an issuer and audience, plug in another check, or pass access: "none" to rely on the credential alone.

Standalone consequence: a public product cannot ask every customer to hold a Cloudflare Access service token. It would run with access: "none" or its own gateway, which makes the credential the only factor.

Sign-in for people

Stub

Projects and workflow

Portable

GET/v1/datastores/{datastoreId}

The datastore the credential is bound to: name, module, API major version, lifecycle and your role.

Projects in the datastore. A project key is 2–10 capitals and digits (ENG); issue keys are ENG-12.

Workflow states, each with a category of todo, in_progress or done, and the allowed transitions. A transition not in the list is 409 workflow_conflict.

Changes and history

Portable
GET/v1/datastores/{datastoreId}/changes?after={seq}&limit={n}

The commit-ordered journal after a sequence number. limit is 1–1000, default 200. Because seq is gapless and in commit order, polling this route never misses a change.

}
GET/v1/datastores/{datastoreId}/issues/{issueId}/history

One issue's journal entries, with before and after values and who made each change.

GET/v1/datastores/{datastoreId}/audit

Management events (grants, credentials, lifecycle). Needs audit.read, the one management permission a service credential may hold.

Sync protocol

Portable

Records implements Replicache-style push and pull semantics against its own backend, without depending on the library. Local changes apply at once; the server's decision always wins; unsent edits are replayed on top.

POST/v1/datastores/{datastoreId}/sync/push
// request
{ "clientGroupId": "tab-group-8f2c", "clientId": "page-1c9e0d",
  "mutations": [ { "id": 7, "name": "projects.transitionIssue",
                   "args": { "issueId": "…", "expectedRevision": 3, "toState": "done" } } ] }

// response: one outcome per mutation
{ "outcomes": [ { "id": 7, "status": "applied", "seq": 42 } ], "head": 42 }
// other statuses: skipped | rejected {code,message} | conflict {code,currentRevision}
//                 pending {actionId}   ← cloudflare-os approvals only
POST/v1/datastores/{datastoreId}/sync/pull

Body {"clientGroupId", "cookie"}, where the cookie is the last seq you saw, or null. The response is {cookie, lastMutationIdChanges, patch}, and the patch is a list of put, del and clear operations over keys such as issue/<id>. It is built from the journal, or from current tables when the cookie is older than retention. Full-state pulls are bounded to 200 projects, 5,000 issues, 20,000 comments and 8 MiB; a larger datastore gets 413 payload_too_large rather than a truncated state.

Standalone note: the pending outcome exists because cloudflare-os can hold a write for human approval. Outside cloudflare-os nothing produces it. A standalone product would either drop it from the public contract or build its own approval rules.

Pokes

Cloudflare runtime: WebSocketPortable: SSE
GET/v1/datastores/{datastoreId}/poke

After each commit, subscribers receive {"datastoreId","head"}. A poke carries no data: pull to get it. Subscriptions are authorised with issues.read on connect and closed after 10 minutes, so a revoked credential stops receiving pokes within that bound.

  • Cloudflare: a WebSocket upgrade, served by one DatastorePokeHub Durable Object per datastore with hibernating sockets.
  • Node: Server-Sent Events with Accept: text/event-stream, from an in-process hub. Several instances share pokes through Postgres LISTEN/NOTIFY with pokes.pubsub: "postgres".

Pokes are best effort. Clients also pull on reconnect and on a 30-second safety timer.

Browser sync client

Portable

@records/sync-client has no runtime dependencies and imports only types from the contracts, so it adds about 7.5 kB gzipped.

import { SyncClient, httpTransport, pokeSource, guardUnload } from "@records/sync-client";

const client = new SyncClient({
  principal: viewer,
  transport: httpTransport(`${base}/v1/datastores/${id}`, fetch,
                           () => ({ authorization: `Bearer ${token()}` })),
  onPoke: pokeSource(new EventSource(pokeUrl), { datastoreId: id }),
});
await client.start();
guardUnload(client);           // warns before closing with unsynced changes

client.subscribe(() => render(client.scan("issue/")));
const h = client.mutate.projects.createIssue({ projectId, title: "Fix login" });
// Shows at once as ENG-? until the server's number arrives by pull.
await h.result;               // confirmed | processed | pending | rejected | conflict

Pending mutations live in memory only. Records deliberately does not persist offline business writes in the browser.

Webhooks

Cloudflare runtime: deliveryVia cloudflare-os: configuration

Events: project.created, project.updated, issue.created, issue.updated, comment.created. A Jira format sends jira:issue_created, jira:issue_updated with a changelog built from the journal, and comment_created.

Delivery is at least once, from the transactional outbox. De-duplicate on X-Records-Delivery.

X-Records-Delivery:  0192f3c1-…
X-Records-Timestamp: 1790000123
X-Records-Signature: sha256=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>
X-Hub-Signature:     sha256=<hex HMAC(secret, body)>     ← Jira format only

Reject a timestamp outside your tolerance; five minutes is the reference default.

Today: the outbox is drained by a Cloudflare Queue consumer and a one-minute cron. The Node server does not deliver webhooks: events accumulate in the outbox until a Worker drains them. Webhooks are created, paused, pinged and inspected only in the cloudflare-os Data page.

SQL analytics

Portable

A read-only records_analytics role sees a versioned analytics schema of views through the same row-level policies, intended for a read replica. The journal's seq gives incremental extraction if you feed a warehouse.

Errors and limits

SDKs

Portable

Both SDKs are generated from GET /v1/openapi.json (OpenAPI 3.1, produced from the Zod contracts). They send idempotency keys automatically, retry only idempotent calls, honour Retry-After, and surface a 412 with the current revision.

  • TypeScript: @records/sdk
  • Python: records-sdk, in the same package's python/ directory
Standalone gap: neither package is published to npm or PyPI, and there is no versioning or deprecation policy for the public contract yet.

Self-hosting

PortableGaps: webhooks, maintenance

The same adapters and contract suite run on Node beside any Postgres 17. The contract suite passes on both workerd and Node against one database.

import { createRecordsServer } from "@records/node";

const server = await createRecordsServer({
  databaseUrl: process.env.RECORDS_APP_URL,        // a login in records_app, not the owner
  publicBaseUrl: "https://records.internal.example",
  access: "none",                                   // or { issuer, audience } for Cloudflare Access
  rateLimit: { limit: 600, windowMs: 60_000 },
  pokes: { pubsub: "postgres" },                     // share pokes across instances
});
console.log(await server.listen(8787, "0.0.0.0"));
  1. Create a Postgres 17 database and apply migrations as the owner: RECORDS_MIGRATION_URL=… pnpm --filter @records/schema db:migrate. Runtime logins cannot run DDL.
  2. Create two logins: GRANT records_app TO … and GRANT records_publisher TO …. Neither may own objects or hold BYPASSRLS.
  3. Bootstrap the organisation and first data administrator with db:bootstrap.
  4. Run migrations before deploying code that depends on them. Rollback never reverses SQL; migrations are additive and roll forward.
Missing on Node: the outbox publisher and webhook delivery, and the hourly maintenance (journal partitions three months ahead, token-claim and outbox pruning). A self-hoster would run these from cron through the ops CLI or a small worker process that does not exist yet. There is also no management UI outside cloudflare-os.

Operations

Portable: scriptsStub: managed backups
  • Backups: nightly pg_dump to object storage with a lifecycle rule and bucket lock. Scripts exist; no bucket or schedule is set up.
  • Restore one datastore: restore a database branch to a point in time, read that datastore's journal up to a chosen seq, and replay it into production as system commands. Other datastores are not rewound. Tested locally.
  • Redaction: an audited procedure that masks named fields in the current row and past journal entries, and records a redact entry.
  • Retention: journal partitions past the window move to cold storage and are detached. Pulls with older cookies get a full reset. No window has been chosen.
Today: the Neon project is on the Free plan with a 6-hour restore window, which the runbook calls inadequate before a team relies on it.
Integration

cloudflare-os

Via cloudflare-os

The cloudflare-os integration lets gadgets read and write Records datastores on behalf of the person using them, with approvals and audit handled by the platform.

How a gadget connects

  1. A person with a membership connects a gadget to a datastore and picks scopes. That creates a binding, revocable from the Data page.
  2. Reads act as the binding (the connecting person's role ∩ its scopes). Every viewer is checked as a datastore reader, and each read is recorded as an observation.
  3. Writes act as the viewer who asked. The gadget UI obtains a one-use, 60-second viewer assertion for the exact intent digest, and the gadget server passes it through.
  4. The gatekeeper redeems the assertion, runs the platform's approval queue, and mints a 60-second delegated token for the Records service. The journal records the viewer as actorId, the binding as actId and via: "gadget".
// gadget UI
const idempotencyKey = crypto.randomUUID();
const digest = await recordsIntentDigest("createIssue", input, idempotencyKey);
const viewerAssertion = await gadget.$createViewerAssertion("RECORDS", digest);
const outcome = await gadget.createIssue(input, { idempotencyKey, viewerAssertion });

// gadget server: pass both through unchanged
return env.RECORDS.createIssue(input, options);
