    How it works

    Many ways in. One way to write.

    Every adapter turns its request into a command and hands it to the same bus. Validation, permissions, workflow rules and history are identical whether the change came from a script, a browser, a Jira client or a cloudflare-os gadget.

    httpNative REST APIIf-Match · Idempotency-Key
    syncOptimistic syncpush · pull · poke
    jiraJira REST subset/rest/api/2 · /rest/api/3
    gadgetPartner appsdelegated JWT, 60 s

    Command bus

    1. Set trusted context: principal, org, datastore, scopes
    2. Replay a known Idempotency-Key
    3. Authorise: role ∩ scopes ∩ command
    4. Run the module handler, check the revision
    5. Take the clock last, write rows and journal
    6. Commit, then poke subscribers

    Features

    Built for data you'll be asked about later.

    Records is for shared business data: the projects, issues and decisions that outlive the app that created them.

    GET …/changes?after=41

    A change feed that can't skip

    A per-datastore clock makes seq gapless and commit-ordered. Poll from any point and you get every change after it, in order.

    GET …/issues/:id/history

    History on every record

    Each change stores the fields before and after, the person, the delegating app, and whether it came in by REST, sync, Jira or a gadget.

    @records/sync-client

    Instant UI, server wins

    Edits apply locally at once and replay on top of what the server decides. A losing edit shows why it lost. About 7.5 kB gzipped.

    If-Match: "r3"

    No silent overwrites

    Every edit names the revision it read. A stale edit gets a 412 with the current revision, so tools can merge or ask.

    records.can()

    Permissions enforced twice

    The service checks role, credential scope and operation. Postgres row-level security checks membership again, so an application bug can't leak another datastore.

    X-Records-Signature

    Signed webhooks

    Issue, project and comment events from a transactional outbox, HMAC-signed with a timestamp. A Jira-shaped format is available for existing receivers.

    replay to seq 4,790

    Restore one datastore

    Replay a datastore's journal from a point-in-time branch into production. Every other datastore stays as it is.

    records_ops.redact

    Erasure without lying

    The journal stores principal IDs, not names. Free text that must go is masked by an audited procedure that leaves its own journal entry.

    analytics.*

    SQL for your BI tool

    A read-only analytics role sees versioned views through the same row-level policies. Point a read replica at your dashboards.

    Security

    Designed to fail closed.

    If Records can't verify who you are, it refuses. If a key server or the replay store is unreachable, it refuses. It never guesses.

    Credentials shown once

    Service credentials are stored as SHA-256 digests, scoped to one datastore, and expire within a year.

    Short, single-use tokens

    Delegated tokens live 60 seconds, are ES256-signed, and are claimed once in a shared replay guard.

    Tenant keys can't move

    Every row carries its organisation and datastore. A trigger refuses any change to either.

    Journal is append-only

    Application roles can insert and read. Update and delete are refused for everyone except the audited redaction procedure.

    No payloads in logs

    Record bodies and credentials never reach logs or platform observations.

    Least-privilege logins

    Runtime logins own nothing, can't run DDL, and never hold BYPASSRLS.

    Questions

    Before you ask.

    What teams usually want to know before they move shared data into Records.

    Is Records a Jira clone?

    No. Projects is one module with its own data model. Its API also speaks a tested subset of Jira's REST API so existing tools work. Boards, sprints, attachments and issue links are not part of that subset.

    Do I need cloudflare-os to use Records?

    No. Records runs on its own and accepts service credentials, OIDC tokens and delegated tokens from any trusted issuer. cloudflare-os is the first platform integration, and it adds gadget connections, viewer-signed writes and approvals.

    What happens when two people edit the same issue?

    Both see their edit at once. The server applies the first; the second is refused with the current revision, and the sync client replaces the losing guess with the server's version and says why.

    Does it work offline?

    Only briefly. Unsent changes are kept in memory, and the page warns before you close it with unsynced edits. Records deliberately doesn't store business writes in the browser.

    Can I get my data out?

    Yes: the REST API, the change feed, Jira clients, webhooks, SQL analytics views, and a full datastore export.
