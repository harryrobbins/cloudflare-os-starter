01 — MODEL

Keep meaning independent.

Your open model defines what the data means. Versioned mappings connect it to database tables and APIs, independently of any particular app.

02 — CONNECT

Let the data travel.

Connect gadgets, other workspaces and external systems to the same datastore through explicit grants. Data outlives the apps using it.

03 — TRUST

Keep the rules together.

Plan for permissions, revision checks and a history of changes at the data boundary, so each new interface follows the same rules.

Built for a different way to build

Leave the suite.
Keep the substance.

Start with shared models and business rules, then build the interfaces that fit. Records is being built for three common starting points.

01 — MOVING ON

Outgrow enterprise software.

Move selected workflows out of Jira or Linear, Slack or Teams, Notion or Confluence. Map the data to open models and replace one interface at a time, with a migration path you control.

02 — STARTING FRESH

Build your own way of working.

Starting a business or a new team? Choose a useful model, adapt it to your domain and create bespoke apps without committing your organisation to a fixed software suite.

03 — BUILDING WITH AI

Give your vibe coding a foundation.

Let AI help build the screens. Give it an explicit model, scoped commands and reusable rules to build against, so every new app does not have to invent the same backend.

More opinionated than starting with backend building blocks. Supabase supplies Postgres, authentication, storage, realtime and APIs. Records focuses on the layer above: shared domain models, mappings, permissions and commands packaged for apps. Enterprise controls and measured scale are delivery requirements; superiority in scale or security is not an established claim. Explore the use cases and trade-offs ↗
02 / At home in cloudflare-os

Give your gadgets
a bigger world.

A small app should be able to work with shared business data. Records is designed to make that connection part of the platform.

  1. Declare what your app needs.

    A blueprint names a module, an API version and the permissions it needs.

  2. Connect an existing datastore.

    The Records connector checks compatibility and grants. Another app can connect to that same data.

  3. Read, act and stay in sync.

    Writes retain viewer identity and approvals. Change notifications prompt connected apps to refresh.

03 / An ordinary, dependable foundation

Your infrastructure.
Your choices.

The recommended stack is Postgres, PostgREST and a small gateway and change relay. Host it alongside your database, and connect from Cloudflare or elsewhere.

Build alternatives to the SaaS workflows you use. Keep control of the data and interfaces as those workflows change.

The first service runs locally on Postgres + PostgREST. Production qualification and live cloudflare-os rollout remain in progress; the on-page explorer is still an illustration.
  • PostgresRelational data, permissions and transactional history. Choose a suitable managed provider or run it yourself.
  • PostgRESTREST reads over approved views, with explicit command functions for meaningful writes.
  • CloudflareA native OS connector. Optional Hyperdrive for trusted SQL callers; HTTP clients use the gateway.
  • Live updatesA relay signals changes. Clients catch up from durable history after reconnecting.
  • AdaptersAnyone can build an SDK or compatibility layer over an open model. A vendor’s conventions are one view, not the definition of your data.
