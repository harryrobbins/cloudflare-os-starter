Proposed next delivery

Build apps on shared meaning.

The Records service is live. These plans describe the next client work; neither blueprint nor the new live cloudflare-os connector is implemented yet.

Adapt a project blueprint

Build a new Work Board and read-only Work Report around the canonical work profile. Keep the existing Project Board and Report available on their legacy backend. The first version supports titles, descriptions and open/active/done states.

Use Jira issue data as a concrete mapping exercise, with Linear as a second adapter example. Vendor IDs and status translations belong to adapters. Assignees, projects, comments and rich workflows need explicit model extensions or an honest import-loss report.

  1. Complete the shared OS connector: enrolled viewers, scoped credentials, durable approvals and observer checks.
  2. Build the read-only report using consistent snapshots and journal catch-up.
  3. Add board commands with exact intent, approval, revision conflicts and safe retries.
  4. Prove two gadgets and an external client converge, then publish new blueprint identities.

A Records Explorer blueprint

Borrow the useful parts of Adminer and phpMyAdmin: a clear data browser, schema inspection, record details and editing. Bind the explorer to authorised Records datastores; it receives no database-owner credentials and exposes no arbitrary SQL console.

  1. Browse an explicitly connected datastore and inspect its model, fields and API contract.
  2. Page through records, inspect bounded change history and show schema-defined relationships where supported.
  3. Add bounded exports and semantic representations through observed host methods.
  4. Later, generate forms for reviewed module commands and show approval, conflict and revocation states.

A searchable datastore registry, server-side filters, richer relations and a browsable audit API are separate service work. The UI must show those limits rather than invent database capabilities.

One shared prerequisite

Both plans use the same credential broker and approval boundary. Browser code never holds service keys. Cached data is cleared when permissions change. Schema publication, role administration and destructive database operations stay in operator tooling.

The downloadable plans include source paths, dependencies, delivery checklists, acceptance tests and rollout limits. Source links in those files refer to the repository.
