Integration foundation

One datastore. Many gadgets.

A blueprint declares a requirement; a binding supplies authority. The datastore persists independently of any one gadget or cloudflare-os instance.

Partial integration, explicitly bounded. A generic TypeScript client and viewer-binding seam exist. The full cloudflare-os broker, enrollment, approval UI and multi-gadget rollout are not wired into production.

Blueprint adaptation and Records Explorer plans → The existing Project Board and Report have not been migrated.

Declare the contract

The client validates a module ID, API major, required entities, commands and scopes against the datastore description. A work board and a report can use the same work module; a messaging inbox and channel view can use the messaging module.

Bind a verified viewer

The read binding requires host callbacks that cryptographically verify a viewer assertion and exchange it for an individually scoped credential. The binding checks issuer, audience, organisation, subject, expiry and returned datastore identity. There is no permissive default verifier or shared viewer credential.

Preserve approval intent

Host writes need the separate exact-intent approval contract. A prior approval cannot override current membership or a revoked binding. Wiring the host credential broker and approval flow remains integration work; a service-principal HTTP demo does not prove viewer attribution.

Synchronise shared views

The API provides consistent bounded snapshots, journal pulls, permission epochs and authorised SSE hints. The local client can reconcile after missed notifications. Host apps must reset private caches when permissions change and provide safe observations to every authorised viewer.

Acceptance still required

Run two real cloudflare-os gadgets and an external client against the same datastore. Prove convergence, attribution, approvals and revocation across enrolled instances. Jira/Linear and Slack/Matrix SDK shapes are optional adapters, not prerequisites for that integration.
